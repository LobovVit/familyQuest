# Версии, релизы и развёртывание

`VERSION` — версия продукта SemVer. Текущий выпуск: `0.1.1`, закрытый SaaS-пилот и домашний режим. Версии backup, политик обучения и npm-зависимостей независимы от версии продукта.

- PATCH — совместимые исправления; MINOR — новые совместимые возможности; MAJOR — несовместимые изменения. До 1.0 несовместимые изменения явно описываются в заметках MINOR-релиза.
- Аннотированный Git-тег `vX.Y.Z` должен указывать на коммит с `VERSION=X.Y.Z`. Опубликованные теги не передвигаются: исправление выпускается новой версией.
- GitHub Actions запускает тесты и сборки для push тега. Только после успеха всех jobs публикуется GitHub Release с заметками. Это не автоматическое развёртывание сервера.
- SHA, версия и UTC-время сборки встраиваются в Go-бинарник, frontend и OCI labels. Они не читаются из текущего checkout во время работы и не подменяются runtime environment.
- Непомеченная сборка имеет суффикс `-dev.<sha>`, изменённое дерево — `-dirty`. Прямая сборка без аргументов показывает `dev/unknown`, а не вымышленный релиз.

## Выпуск

1. Изменить VERSION и документацию, проверить совместимость/миграции, выполнить тесты, commit и push.
2. На чистом дереве создать аннотированный тег: `git tag -a "v$(cat VERSION)" -m "FamilyQuest $(cat VERSION)"`.
3. Опубликовать конкретный тег: `git push origin "v$(cat VERSION)"`. Дождаться зелёного CI и GitHub Release. Для main предпочтителен merge проверенного PR; тег фиксирует конкретный коммит независимо от дальнейшего движения ветки.

## Сборка и установка

Из корня репозитория в bash: `source scripts/build-metadata.sh`, затем обычная Compose-сборка. Один набор метаданных применяется к API и web. Для ручного `docker build` передавать `--build-arg APP_VERSION --build-arg APP_COMMIT --build-arg APP_BUILT_AT` обоим образам.

Сервер: `RELEASE_TAG=v0.1.1 bash scripts/update-home.sh`. Требуются git, Docker Compose, curl и Python 3. Скрипт проверяет чистоту дерева, тип и значение тега, переключается в detached HEAD, собирает оба образа, ждёт health и сравнивает SHA публичного `/api/version` и запущенных контейнеров. Без RELEASE_TAG обновляется BRANCH (по умолчанию main); такая сборка может быть dev. `ALLOW_DIRTY` больше не допускает публикацию изменённого дерева.

Перед обновлением сохранять backup БД и предыдущие образы, особенно если есть миграции. Скрипт не откатывает миграции и не выполняет автоматический rollback. После ошибки проверки выяснить, что реально запущено. Не откатывать SaaS на старый домашний режим. Разделение runtime/admin и подключение семей — в [SaaS-инструкции](saas-operations.md).

## Проверка работающей версии

`GET /api/version` публичен в обоих режимах и возвращает `version`, полный `commit`, `builtAt`, `startedAt`. Заголовок Cache-Control: no-store. Данные семьи и секреты не раскрываются. `startedAt` — запуск API-процесса, а не время выпуска релиза; UTC timestamps отображаются браузером в местном времени.

Внизу страницы «О приложении» показывает сервер и загруженный интерфейс отдельно. Если SHA различаются, пользователь видит предложение обновить страницу. Если API недоступен, версия сервера не угадывается. Перечитать серверную версию можно перезагрузкой страницы; для ошибки доступна кнопка повтора.

До этой доработки на 10.66.66.6 был checkout be003eb, включающий SaaS-коммит 07cb1a0, и frontend index-BjVG8hco.js. `/api/config` возвращал `saas:false`: код пилота установлен, многосемейный режим не включён. Прежние образы не содержали точного build SHA, поэтому checkout сам по себе не является криптографическим доказательством идентичности работающего бинарника.

Тег v0.1.0 сохранён в истории, но его release CI остановился на проверке аннотированного тега: shallow checkout создал ссылку на commit вместо tag object. В v0.1.1 контейнерная job использует fetch-depth: 0. Выпуск v0.1.0 на сервер не устанавливался.
