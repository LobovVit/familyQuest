> Исторический снимок первоначального аудита **до изменений кода**. Ограничения ниже не описывают итоговую реализацию. Текущее состояние: [SaaS-архитектура](saas-architecture.md), [эксплуатация](saas-operations.md), [итог внедрения](implementation-2026-09-26.md).

## Вывод

Основа пригодна для дальнейшего развития: направление зависимостей проверяется тестами, сценарии отделены от HTTP/SQL, есть серверные проверки ролей, отзыв сессий, транзакции и идемпотентность начислений. Переписывать проект или переходить на микросервисы для следующего этапа не требуется.

**Общая установка для нескольких внешних семей пока не готова.** Текущая безопасность действует внутри одной семьи. Наличие роли parent и папки family не означает tenant isolation. Подготовлена [целевая архитектура](saas-architecture.md); выбранная пользователем модель — подписка на семью с лимитом детских профилей.

## Подтверждённые ограничения

Приоритет P0 ниже означает блокер общего SaaS-запуска, а не новую регрессию домашней установки.

| Приоритет | Факт и источник | Последствие / необходимое изменение |
| --- | --- | --- |
| P0 | [Principal и Participant](../backend/internal/domain/domain.go) не содержат семьи; [Repository](../backend/internal/application/service.go) и [SQL](../backend/internal/store/store.go) используют глобальные ID/списки | Любой parent действует в масштабе установки. Нужен scope во всех сценариях и составные связи в БД |
| P0 | [Маршруты](../backend/internal/httpapi/server.go): participants и leaderboard без authorize; [familyRoutes](../backend/internal/httpapi/family.go): overview тоже публичен | Публикуются имена, рейтинг, названия занятий и прогресс. Перевести на вход в конкретную семью вместе с новым login UX |
| P0 | [ImportBackup](../backend/internal/store/backup.go) блокирует все таблицы, делает TRUNCATE и RESTART IDENTITY | Восстановление одной семьи уничтожило бы остальные. Семейный import должен переписывать ID/ссылки и затрагивать только её данные |
| P0 | [Device store](../backend/internal/store/devices.go): глобальное управление, связь с участником без семьи | Привязка, подтверждение родителя и отзыв должны проверять принадлежность одной семье |
| P0 | [Миграции](../backend/migrations/001_init.sql): глобальные UNIQUE имени/названий и FK без tenant; [family store](../backend/internal/store/family.go) хранит ссылки в JSONB | Нельзя создавать одинаковые имена в разных семьях; добавление фильтра к одному endpoint не защищает связи внутри карточек |
| P1 | Нет adult account, membership, регистрации семьи, приглашений и восстановления взрослого аккаунта; вход через [Login](../backend/internal/application/login.go) | Нужна самостоятельная onboarding/identity-модель, отдельная от детского PIN |
| P1 | Participant не содержит дату рождения; [StartMath](../backend/internal/application/learning.go) валидирует клиентские настройки без возраста; [ReadingTraining](../frontend/src/features/learning/ReadingTraining.tsx) даёт выбор уровня | Уровень не адаптируется к ребёнку. Требуются серверная возрастная политика, override родителя и snapshot занятия |
| P1 | Нет таблиц/сценариев subscriptions/payments/plans/реестра семей | Нельзя достоверно посчитать оплаченные семьи, срок доступа и детские места. Это отдельный модуль, не boolean на участнике |
| P1 | [Операции](operations.md): нет автоматического offsite backup; семейные коллекции без пагинации, медиа в JSONB | Для внешних семей нужны восстановление, квоты, мониторинг и нагрузочная проверка |
| P2 | Широкий Repository, крупный [Workspace](../frontend/src/features/FamilyQuestWorkspace.tsx), побочные эффекты GET плана и зависимость рейтинга от текущих назначений | Делить по новым сценариям постепенно. Исторический рейтинг нельзя использовать как финансовый журнал |

Существующие тесты подтверждают границы слоёв и single-family сценарии; они не являются доказательством безопасности нескольких семей. В частности, PostgreSQL-тесты сейчас работают с одной общей областью данных, без RLS и пары семей A/B.

## Что изменено в этом пересмотре

- Добавлена спецификация SaaS: схема сущностей, вход, SQL/RLS, JSONB, возрастные уровни, подписки/платежи, реестр, миграция и критерии приёмки.
- README приведён к текущим rewardVersion=3, лимиту математики 40 ⭐ и backup v5; добавлено чтение с отдельным лимитом 30 ⭐.
- В API добавлен пропущенный публичный overview. В архитектуре и эксплуатации явно разделены текущая одна семья и будущий сервис.
- Исполняемый код и SQL-миграции в рамках этого пересмотра не изменялись. Изоляция, возрастные настройки и биллинг остаются работой следующего этапа; частичная миграция не выдаётся за готовый сервис.

На старте рабочее дерево уже содержало staged/unstaged изменения чтения, математических наград, backup v5 и документации. Они сохранены; проверялась текущая совокупная рабочая версия. Commit, push и deployment не выполнялись.

- `go -C backend vet ./...`: успешно.
- `npm --prefix frontend test`: 68 тестов, 19 файлов — успешно.
- `npm --prefix frontend run lint` и `npm --prefix frontend run build`: успешно.
- Локальные ссылки Markdown и `git diff --check`: проверены после правок документации.

Вызовы Go выполнялись с очищенным GOROOT. Проверки версии production, браузерный smoke, security dependency scan, нагрузка, реальные платежи и полноценное восстановление на новом сервере в этот пересмотр не входили. Нового UI нет.

Home Local AI использован дважды: для ревью рисков и сценариев подписки. Его предложения проверялись вручную. Ошибочные ответы, допускавшие двух детей на одно свободное место и зависимость истечения доступа от cron, отвергнуты; общие утверждения о конфликтах SET LOCAL не приняты без доказательств. Семантика RLS и SET LOCAL сверена с официальной документацией PostgreSQL, ссылки включены в проект архитектуры.

## Порядок реализации

1. Identity, семья и сквозная изоляция вместе с безопасным backup; приёмка двумя семьями и отдельной runtime-ролью PostgreSQL.
2. Возраст ребёнка, настройки по предмету и серверное применение при начале занятия, без пересчёта истории.
3. Подписка с лимитом детей, платежный журнал и операторский реестр; provider adapter после выбора рынка и провайдера.
4. Эксплуатационные проверки и закрытый пилот, затем продажи.

Цена, число мест, trial/grace и возрастная методика не объявлены согласованными; в спецификации они явно отделены от принятой модели оплаты.
