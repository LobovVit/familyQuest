# Создание семьи и её название

Новый клиент входит через общий аккаунт LOVIT. Если его `issuer + subject` ещё не
привязаны к FamilyQuest, приложение предлагает название семьи, имя первого
родителя и PIN из шести цифр с подтверждением. После создания открывается выбор
профиля; для входа нужен PIN. Родитель меняет название в **Настройки пользователей
→ Семья и подписка**. Название сохраняется в каталоге конкретной семьи и видно
в её подписке, в том числе в проекции для портала LOVIT.

Создание семьи не включает оплату или бесплатный период: `plan=registered`,
`access_until=now()`, `paid=false`. Действия с семейными данными требуют активного
доступа по прежним правилам. Название можно менять и без оплаченного доступа.
Регистрация общего аккаунта, восстановление пароля и активация подписки относятся
к соответствующим сервисам LOVIT; этот шаг создаёт пространство FamilyQuest.

## API и границы

- `POST /api/account/exchange` и `/api/account/restore` возвращают прежний массив
  профилей существующему клиенту либо `{"onboarding":true}` новому.
- Сессия создания семьи действует 30 минут. Она не даёт доступа к данным семьи
  или семейным JWT. Перезагрузка страницы восстанавливает форму.
- `POST /api/account/family` принимает только `name`, `parentName`, `pin`.
  Название и имя: 1–80 Unicode-символов после удаления пробелов по краям,
  без управляющих символов. Identity берётся только из серверной OIDC-сессии.
- Access вызывает закрытый Provisioner с отдельным служебным ключом.
  В одной SQL-транзакции создаются каталог, схема, роль, родитель с bcrypt PIN,
  связь identity и членство Core в семейной роли. PIN не попадает в журнал или
  очередь. Повтор по той же identity не создаёт вторую семью, не меняет PIN,
  название или подписку. Блокировка существующей семьи не обходится регистрацией.
- `PUT /api/family/name` принимает только `name`. Нужна сессия родителя своей
  семьи и обычная CSRF-проверка. ID семьи клиент не передаёт. Core имеет
  `UPDATE(name)` в каталоге; права на тариф, статус и платежи не расширяются.
- Access сохраняет read-only доступ к каталогу и не получает семейных SQL-ролей.
  Provisioner не публикует порт на хосте и не подключается к edge-сети.
  Его DB-учётная запись имеет операторские DDL-права и доступна только ему.
- На аккаунт действует ограничение попыток; существующий лимит сессий также
  сохраняется. Распределённые rate limits и несколько реплик Access не добавлены.

## Установка

Требуются уже настроенные Access, Core и OIDC. Без дополнительного overlay
прежний операторский сценарий создания семьи продолжает работать.

1. Сохранить dump PostgreSQL, роли/grants, `.env`, том сессий и прежние образы.
2. Добавить в защищённую `.env`:

   ```dotenv
   # Отдельный случайный ключ длиной не менее 32 байт; не ACCESS_SHARED_SECRET.
   PROVISIONER_SHARED_SECRET=<dedicated-random-secret>
   PROVISIONER_DATABASE_URL=postgres://<operator>:<password>@postgres:5432/familyquest?sslmode=disable
   CORE_DATABASE_ROLE=familyquest_runtime
   ```

3. Собрать новый backend-образ. С операторским `DATABASE_URL` выполнить
   `familyquest-operator migrate`, затем `grant-core` с
   `{"Role":"familyquest_runtime"}` (подставить фактическую роль Core).
   Каталог `accounts` переводится с email PK на family_id PK, email остаётся
   уникальным, но допускает NULL вместе с password_hash для OIDC-only владельцев.
   Существующие адреса, хеши, семьи и identity сохраняются. Миграция повторяема.
   Семейные миграции применяются существующей командой, новых tenant-миграций нет.
4. Создать `.self-registration-enabled` рядом с `.access-proxy-enabled`.
   `scripts/update-home.sh` подключит `docker-compose.onboarding.yml`.
   При ручном запуске использовать все три Compose-файла:

   ```bash
   docker compose -p familyquest -f docker-compose.prod.yml -f docker-compose.access.yml -f docker-compose.onboarding.yml up --build -d --wait
   ```

5. Проверить `/api/health`, SHA API/Access/Web, вход существующей семьи и полный
   сценарий нового тестового аккаунта, изменение названия и его повторное чтение.
   Удалять тестовую семью только по её точной тестовой identity/ID.

Безопасный откат функции: убрать marker/overlay и обновить Access/Web до прежней
согласованной сборки. Самостоятельное создание станет недоступно; уже созданные
семьи и OIDC-привязки сохраняются. **Не возвращать NOT NULL/PK email** при наличии
OIDC-only аккаунтов. Старый операторский `registry` не понимает NULL email — для
управления реестром оставить обновлённый operator binary.

## Проверки

Интеграционный `TestSelfRegistrationEndToEnd` использует одноразовую PostgreSQL,
реальный тестовый OIDC provider, Access, private Provisioner и Core с разными
SQL-ролями. Проверяет создание, PIN, сохранение названия, запреты для ребёнка,
CSRF, идемпотентность, разные identity, изоляцию SQL, блокировку семьи,
совместимость старых парольных аккаунтов и повторную миграцию. UI-тесты покрывают
подтверждение PIN, повторную отправку, ошибки, повтор попытки и сохранение названия.
