# Yandex Cloud и YDB Serverless для FamilyQuest

Проверено 26.09.2026 по официальным источникам. Облачная инфраструктура не создавалась, данные не переносились. Решение: **для ближайшего пилота сохранить PostgreSQL; перенос приложения в Yandex Cloud рассматривать отдельно от замены СУБД**.

## Сравнение вариантов

| Вариант | Что сохраняется | Что потребуется | Решение |
| --- | --- | --- | --- |
| Compute Cloud + PostgreSQL на VM | Текущие контейнеры, транзакции, SQL-роли, семейный backup | Сеть/TLS, offsite backup, мониторинг, обновление и ответственность за БД | Наиболее прямой путь для текущего закрытого пилота; одна VM не даёт HA |
| Compute Cloud + Managed PostgreSQL | Основная SQL-модель и pgx | Проверка managed-ролей, private network/TLS и restore; фиксированная стоимость кластера | Предпочтительное направление после проверки управления ролями |
| Serverless Containers + PostgreSQL | Go-приложение после адаптации | Ограничение соединений, миграции отдельным job, вынос больших import/export и медиа | Текущий API нельзя переносить без изменений |
| Serverless Containers + YDB Serverless | Домен и application-порты | Новый persistence adapter, ключи/индексы, транзакции/retry, изоляция, проекции, backup | Отдельный эксперимент; сейчас не заменяет PostgreSQL |

## Почему YDB не является заменой строки подключения

Managed YDB Serverless документирует YQL/YDB SDK и Document API. Совместимость PostgreSQL в опубликованном руководстве YDB v25.3 имеет ограничения и описана как тестирование в Docker; это не подтверждение совместимости текущего pgx-приложения с облачным Serverless endpoint. [Yandex Cloud](https://yandex.cloud/ru/docs/ydb/pricing/serverless), [YDB PostgreSQL compatibility](https://ydb.tech/docs/en/postgresql/statements/update?version=v25.3).

В нашем store используются pgx, bigserial/sequence, FK/CHECK, ON CONFLICT, JSONB-операторы, lateral-проекции рейтинга, блокировки строк/таблиц, PostgreSQL advisory lock и repeatable-read export. Добавлена изоляция через SQL-схемы и роли. Совместимость каждого механизма с целевым YDB API ещё не проверена: порт должен переопределить эти механизмы, а не маскировать их PostgreSQL-протоколом.

У YDB есть транзакции Serializable. Это позволяет проектировать атомарные начисления и лимит профилей, но требуется корректная обработка повторов при конфликте. Сетевые побочные действия и выдачу наград нельзя повторять вне идемпотентной транзакционной модели. [Транзакции YDB](https://ydb.tech/docs/en/concepts/transactions), [управление транзакциями SDK](https://ydb.tech/docs/en/recipes/ydb-sdk/tx-control).

Для прототипа YDB ключи семейных таблиц должны включать family_id; схемы PostgreSQL туда автоматически не переносятся. Все проверки принадлежности связей, включая ID внутри JSON, должны сохраниться. Нужны отдельные тесты A/B, повторов ответов/платежей, гонки последнего детского места и экспорта согласованного снимка. Сначала переносится один ограниченный сценарий на синтетических данных, затем измеряются RU и задержки. Второй работающий backend в этом изменении не добавлялся.

## Ограничения serverless-размещения

Serverless Containers ограничивает размер HTTP-запроса **и ответа** 3,5 MB. Наш JSON-import допускает 64 MiB, export может быть больше. Поэтому для такого размещения нужны приватный Object Storage, загрузка по ограниченному подписанному URL, фоновый import/export и статус задания. Медиа также следует вынести из JSONB. Иначе часть семей потеряет возможность восстановления даже при небольшом числе HTTP-запросов. [Лимиты Serverless Containers](https://yandex.cloud/ru/docs/serverless-containers/concepts/limits).

Пул PostgreSQL должен иметь общий бюджет соединений на все экземпляры API. Для нынешней модели роли задаются внутри транзакции и снимаются при commit/rollback; это нужно перепроверить через выбранный proxy/pooler. Автомиграции и создание SQL-ролей не должны выполняться при холодном старте каждого контейнера.

Managed PostgreSQL имеет собственные роли и правила их назначения через интерфейсы Yandex Cloud; документация предупреждает о переопределении назначения GRANT при операциях с БД. Поэтому CREATE ROLE/GRANT/SET ROLE и сохранность семейных разрешений после managed-операций — отдельный блокирующий acceptance-тест. Выдавать API широкие mdb_read_all_data/mdb_write_all_data ради обхода проблемы нельзя. [Управление ролями](https://yandex.cloud/ru/docs/managed-postgresql/concepts/roles).

## Стоимость YDB: ориентир, не бюджет проекта

В официальной таблице для региона Россия на дату проверки: первый 1 млн RU/месяц не тарифицируется, далее 24,64 ₽/млн RU; первые 720 ГБ·час хранения бесплатны, далее 0,0342 ₽/ГБ·час. Эти значения относятся к конкретной валюте/региону и не являются предложением для белорусского юридического лица. [Таблица тарифов в репозитории документации Yandex Cloud](https://github.com/yandex-cloud/docs/blob/master/md-docs/ydb/pricing/serverless.md).

Для 30 дней без provisioned capacity приближённая модель только операций и основного хранения:

`max(RU − 1 000 000, 0) / 1 000 000 × 24,64 + max(GB × 720 − 720, 0) × 0,0342`.

| Допущение, не измеренная нагрузка | Только RU + основное хранение / месяц |
| --- | ---: |
| 1 млн RU, 1 ГБ | 0 ₽ |
| 10 млн RU, 10 ГБ | ≈ 443,38 ₽ |
| 100 млн RU, 50 ГБ | ≈ 3 645,94 ₽ |

Один HTTP-запрос не равен одной RU: рейтинг, JSON, индексы, транзакции и повторы меняют стоимость. Не включены вычисления API, балансировщик, Object Storage/операции, журналы, backup/restore, трафик, поддержка и разработка нового адаптера. Цены Managed PostgreSQL/VM здесь не выдумываются: без региона, HA, размеров, типа плательщика и измеренной нагрузки корректного сравнения полной стоимости нет.

## Предлагаемая схема переноса

1. Отдельные staging/prod folder, VPC/private DB, Container Registry; секреты в Lockbox, права service account по назначению, запрет публичного PostgreSQL.
2. Первый staging: Compute API + web с HTTPS на одном origin; PostgreSQL с текущими проверенными правами. Managed PostgreSQL выбирать после теста ролей. Не включать домашний режим по публичному адресу.
3. Проверить восстановление полной БД и SQL-ролей, затем две семьи, отзыв устройств, платежный журнал и возрастные занятия на staging. Настроить внешние backup, алерты и бюджет.
4. Выделить окно переноса: заморозка записи → dump/restore → контрольные количества/награды/оплаты → вход/изоляция → переключение DNS → наблюдение. Старую БД оставить read-only до завершения проверки. Rollback учитывает новые записи после переключения.
5. Object Storage и jobs для больших файлов, затем отдельная оценка serverless compute. Эксперимент YDB проводить без производственных детских данных и без одновременного переключения клиентов.

Перед фактическим развёртыванием нужны cloud/folder/region, бюджет, домен, модель доступности и проверка правил обработки детских данных для выбранных стран. Для исследования варианта они не требовались; ни облачный контракт, ни расходы сейчас не создавались.
