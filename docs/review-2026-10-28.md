# Аудит архитектуры и документации — 28.10.2026

Проверка охватывает Go domain/application и адаптеры, React/TypeScript, SQL-изоляцию, транзакции и восстановление, авторизацию профилей, SSO/MCP, Docker/Nginx, CI и документацию. Проверялось рабочее дерево ветки `dev/multiproduct-billing`, включая уже существовавшие незакоммиченные изменения MCP. Они сохранены; аудит не является отчётом о развёртывании.

## Архитектурный вывод

Внутренние слои соблюдают направление зависимостей Clean Architecture: backend application зависит от domain и портов, PostgreSQL/JWT/HTTP подключаются снаружи; frontend domain не зависит от React, application получает gateway/session/backup через composition root. Бизнес-инварианты и атомарность дополнительно защищены транзакциями и ограничениями PostgreSQL.

Полной независимости от фреймворков и идеального разделения ответственности нет. React hooks составляют application frontend; доменные структуры содержат JSON-теги; агрегированный Repository широк; часть координации политик остаётся в SQL-адаптере. Access импортирует общий HTTP-контракт из httpapi. Эти ограничения перечислены ниже как технический долг, а не скрыты за успешным тестом импортов.

## Сохраняемые решения и технический долг

1. **Repository/Service и большой workspace.** Агрегированный порт и `FamilyQuestWorkspace` усложняют независимое развитие сценариев. Следующий полезный шаг — выделять отдельные прикладные сервисы и узкие порты по конкретной функциональности, сохраняя одну точку сборки. Массовое механическое разбиение без изменения границ не выполнялось.
2. **Политики в persistence.** SQL-адаптер координирует возрастные ограничения, лимиты мест и выдачу наград под блокировками. Чистые правила по возможности уже в domain. Дальнейшее выделение должно сохранить атомарность: нельзя переносить проверку до транзакции и создавать гонку check/write. Политика подписки проверяется перед операцией; это не гарантия немедленной отмены уже исполняющегося запроса при параллельной блокировке семьи.
3. **Чтение с побочным эффектом.** `ListTasks` лениво создаёт плановые задачи, в том числе при MCP `get_results`; read-only делегирование не может отмечать задачи, но чтение может материализовать план. При истёкшем доступе генерация отключается. Для строгой семантики read-only нужно разделить формирование плана и запрос истории; текущий контракт планера сохранён.
4. **Границы адаптеров.** Общие wire types/CSRF/HTTP route policy пока находятся в httpapi и используются Access. Исключение явно закреплено тестом. При независимых релизах нужен отдельный версионируемый контракт. Некоторые старые методы чтения не принимают Principal: они безопасны только за уже разрешённым семейным Service и транспортной авторизацией; их нельзя произвольно публиковать как новые MCP tools.
5. **Масштабирование.** Отдельная схема/роль на семью подходит текущему пилоту, но увеличивает стоимость миграций. Списки без пагинации, JSONB-медиа, отдельные SQL-проекции и большие backup требуют нагрузочной оценки перед ростом. Файловый SSO-реестр и rate limiter рассчитаны на один экземпляр; горизонтальное масштабирование требует согласованного общего состояния. Универсальный биллинг в этом репозитории остаётся проектным направлением, а не подтверждённым вторым продуктом.
6. **Контракты и эксплуатация.** API описан вручную, OpenAPI/генерация клиентов отсутствуют. Проверка ссылок не проверяет внешние URL и якоря. Offsite-backup, restore drills и внешний мониторинг требуют эксплуатационной настройки. Домашний публичный просмотр сохраняет раскрытие имён/агрегированных результатов; закрывать его нужно на внешней границе согласно [инструкции](operations.md).
