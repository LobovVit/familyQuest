# Telegram Mini App — Семейные дела

Mini App добавляет `/telegram` к существующему интерфейсу. Базовый релиз
`b71db55` с миграцией 011 развёрнут на production 02.11.2026. Обычный веб-сценарий
проверен на production через публичный API и браузер; Telegram и фоновый отправитель
остаются выключенными по указанию владельца. Это **не приёмка реального Telegram**. Названия «Семейные дела» и «Делодень» сохранены; технические
`productId` и `botId` — `familyquest`.

## Сценарий

1. Открыть Mini App из своего продуктового бота.
2. При отсутствии связи открыть страницу `/telegram` **Portal** в обычном браузере,
   войти в существующий аккаунт, получить код и ввести его в Mini App. Затем в Portal
   проверить numeric Telegram ID и явно подтвердить связь. Сам ввод кода не связывает
   аккаунты. Совпадение имени, username, email или телефона ничего не даёт.
3. Явно выбрать семью, затем профиль и его PIN. Текущая модель продукта — одна семья
   на точную пару OIDC issuer + subject; даже единственная семья не выбирается сама.
   Создание второй семьи при входе через Telegram отсутствует.
4. В родительском профиле выбрать ребёнка в планере, открыть «Назначить дело»,
   воспользоваться существующим каталогом, подтвердить выполненное оценкой 1–5.
   Подтверждение начисляет предусмотренные продуктом звёзды. Повтор той же оценки
   обновляет существующее подтверждение, а не суммирует награду.
5. «Выбрать семью» сбрасывает профиль и серверный семейный контекст; снова нужен PIN.
   Переключение на детский профиль использует прежний PIN и прежние серверные ограничения.
   Собственный Telegram-аккаунт ребёнку не требуется.

«Настройки → Семья и подписка» по-прежнему позволяет переименовать семью.
Самостоятельное создание семьи сохраняется в обычном OIDC-входе. Оно не активирует
подписку. Неподключённому/приостановленному аккаунту Mini App не создаёт новую семью
и не присваивает роль родителя. Приглашения и guest-доступ в этой версии продукта
не добавляются: URL и `start_param` не предоставляют никаких прав.

## Границы интеграции

Владелец общего контракта — соседний проект `lovitPortal`, документ
`docs/telegram-mini-apps-contract.md`, версия v1.1 (durable binding, Portal schema 13) от 02.11.2026. Имена JSON-полей и
маршруты сверены также с его `internal/platform/telegram.go` и
`internal/application/telegram.go`; эти файлы из FamilyQuest не изменяются.

Access вызывает Portal через серверный HTTPS-клиент:

| Операция | Portal | Локальный вход |
| --- | --- | --- |
| Проверить подписанный Telegram запуск | POST `/v1/telegram/exchange` | POST `/api/telegram/exchange` |
| Проверить живую связь | POST `/v1/telegram/session` | POST `/api/telegram/session`, каждый защищённый API-запрос |
| Предъявить код | POST `/v1/telegram/link/claim` | POST `/api/telegram/link` |
| Выход | POST `/v1/telegram/logout` | POST `/api/telegram/logout` |
| Согласие/отказ | POST `/v1/telegram/notifications/consent` | POST `/api/telegram/consent` |
| Постоянная привязка | POST `/v1/telegram/notifications/binding` | после согласия и проверки родительского PIN/доступа |
| Проверка актуального согласия | POST `/v1/telegram/notifications/eligibility` | перед каждой попыткой отправки worker |
| Нейтральное уведомление | POST `/v1/telegram/notifications` | worker после транзакционного завершения задачи в Core |

Telegram initData передаётся только в POST body. HMAC, возраст initData, replay,
привязка и отзыв принадлежат Portal. В FamilyQuest нет копии этих правил и нет
бот-токена. Portal `sessionToken` хранится только в памяти Access за случайной
HttpOnly cookie; frontend его не получает. Сессии ограничены сроком Portal,
не продлеваются, теряются при рестарте Access. Нужно заново открыть Mini App.
Развёртывание v1 рассчитано на **один экземпляр Access**, как реестр SSO-сессий.

Cookie Telegram в HTTPS использует Secure, SameSite=None и Partitioned для
встроенного Telegram Web; локальный HTTP loopback — SameSite=Strict.
Изменения требуют существующие CSRF-проверки Origin / X-FamilyQuest.
`X-FamilyQuest-Client: telegram` выбирает Telegram-режим. В нём обязательны cookie,
живой Portal `/session`, точная локальная связь семьи и профильный Bearer, выданный
после PIN. Запомненный веб-профиль не заменяет PIN. Ошибка Portal, неверный продукт,
бот, issuer, subject, истечение или отзыв закрывают этот путь доступа.

Обычные OIDC cookie и browser storage профиля независимы от Mini App. Отсутствие
заголовка Telegram не даёт обхода: тогда нужен обычный SSO-вход; Core в обоих режимах
проверяет профиль, роль, семейную SQL-схему, версии сессий и действующие права.
Платные операции при отсутствии доступа запрещаются прежними проверками.

`accountCore` повторно проверяет точную identity и использует приватную операцию
Core только для списка профилей/PIN. Внутренний JWT владельца никогда не возвращается
браузеру до подтверждения PIN. Все изменения задач, назначений, наград и названия
семьи выполняются прежними use cases; отдельных Telegram бизнес-правил нет.

## Уведомления

Включение доступно только текущему активному родительскому профилю своей семьи.
Кнопка запрашивает право бота писать и отдельное согласие через Portal. Если право
только что выдано, может понадобиться заново открыть Mini App: Portal доверяет
подписанному `allows_write_to_pm` или private `/start`, а не ответу JavaScript.
`/start` сам по себе не означает согласия. Отключить можно в Mini App, через
`/stop`/`/unsubscribe` боту или отвязать Telegram в Portal.

В таблице `notification_recipients` семейной SQL-схемы сохраняются recipientRef,
issuer/subject, ID взрослого, локальное поколение согласия UUID и постоянный
Portal `bindingId`. Файла получателей и зависимости от его тома больше нет.
UI-сессия и её `sessionToken` не нужны worker: закрытие Mini App, истечение её
сессии или рестарт Access не удаляют согласие и очередь.

Включение: проверка живой identity, выбранной семьи, родительского PIN и текущего
доступа → Portal consent → binding с точным совпадением identity → запись Core.
При ошибке сохранения отправляется компенсирующий opt-out; ошибка остаётся видимой.
Повтор согласия для той же привязки и родителя сохраняет локальное поколение и
ожидающие события. Новая привязка создаёт новое поколение, старые события отменяются.
При отказе Core сначала сохраняет отключение и отменяет pending, затем вызывается
Portal. Оба обращения предпринимаются даже при отказе одного; частичный сбой
не выдаётся за успех. До выбора семьи доступен remote opt-out, а worker отменит
старые локальные события при проверке отозванной привязки.

`CompleteTask` сохраняет выполнение и строки `notification_outbox` **одной
транзакцией PostgreSQL** в SQL-схеме семьи. Ошибка INSERT откатывает задачу; ошибка
ответа клиенту после commit не удаляет событие. Запись включает только UUID события,
ID задачи для локальной диагностики и снимок взрослого получателя/поколения согласия.
Источники — обычный веб, Mini App и MCP: они используют одну операцию Core.
Подписка, появившаяся после действия, старое событие не получает.

Access worker отдельно от пользовательского HTTP-запроса обходит каталог семей и
обращается только к приватным Core-маршрутам `notifications/claim`, `check`, `settle`.
SQL-права Access остаются прежними: только чтение каталога, без доступа к семейным
таблицам. Claim использует `FOR UPDATE SKIP LOCKED`, аренду на 60 секунд и случайный
lease token. Одна запись находится у одного живого worker; упавший процесс не мешает
повторному захвату после истечения аренды. Завершение и retry используют CAS по
действующему lease token; устаревший worker не меняет запись.

Перед отправкой проверяются точная identity семьи, текущее поколение SQL-согласия,
совпадение binding, активная роль родителя и действующий доступ к продукту.
Затем Portal eligibility проверяет четыре сохранённых поля привязки. `/stop`,
блокировка бота или unlink отзывают её в Portal; подтверждённый отказ отменяет
все pending этого поколения и отключает его в Core. Новое согласие не восстанавливает
старые события. Устаревший worker с прошлой арендой не может отключить новое поколение.
Portal повторно проверяет binding при enqueue и непосредственно перед отправкой.

В Portal передаются `recipientRef`, `bindingId`, `issuer`, `subject`, постоянный
для строки outbox `eventKey=familyquest-<UUID>` и `template: activity`. Это закрытый
server-to-server контракт; в сообщение не попадают имена детей, названия задач,
оценки, фото, PIN или токены. При retry сохраняется весь payload и тот же eventKey.
После timeout, потерянного 202 или сбоя локального ack повтор дедуплицируется Portal.
Состояние `delivered` означает постановку в долговечную очередь Portal с
`notificationId`, а не подтверждение прочтения в Telegram.

Сетевые ошибки, 429/5xx и ошибки credentials/product configuration повторяются
без предельного числа попыток: 5, 10, 20… секунд, максимум час между попытками.
Backoff хранится в БД; рестарт его не обнуляет. Ошибки payload/конфликта ключа
остаются как `failed` для оператора; отзыв согласия — `cancelled`. Ошибка ack оставляет
исходную строку с арендой, а не выдаёт ложный успех. Состояния и число попыток
сохраняются, терминальные строки автоматически не удаляются.

Доставка **до очереди Portal** — at least once с его дедупликацией. Telegram API
не предоставляет exactly once: статус неопределённой доставки и последующие
попытки sendMessage принадлежат Portal по общему контракту. Продукт не заменяет
его worker и не повторяет Telegram-вызовы самостоятельно.

Семейный JSON-backup не содержит интеграционных метаданных. Восстановление backup
в общей транзакции отменяет pending, отзывает SQL-подписки и сохраняет аудит
доставленных строк. После восстановления требуется новое согласие. Полный
PostgreSQL backup, напротив, должен включать обе таблицы outbox; при восстановлении
старого состояния повтор с прежним UUID безопасен благодаря дедупликации Portal.

Диагностика оператором без записи и без вывода identity получателей:

```bash
# DATABASE_URL — штатное защищённое окружение оператора; вывод содержит только агрегаты.
printf '%s\n' '{"familyId":123}' | familyquest-operator notification-status
```

Команда показывает включённых получателей, pending/leased/retrying, deliveredToPortal,
cancelled/failed, возраст старейшего pending, максимальное число попыток и коды
нерешённых ошибок. Она не включает worker и не отправляет сообщения. `failed>0`,
рост возраста pending или повторяющиеся ошибки credentials требуют проверки
оператором. При намеренно выключенном worker накопление pending ожидаемо.
Логи retry/failed содержат family ID, UUID события, номер попытки и код ошибки.

Подробности в **нужной семейной схеме** (`public` у legacy-семьи), без изменения данных:

```sql
SELECT state, count(*), min(created_at) AS oldest
FROM fq_family_123.notification_outbox GROUP BY state;
SELECT id, state, attempts, available_at, lease_until, error_code, portal_id
FROM fq_family_123.notification_outbox
WHERE state IN ('pending', 'failed') ORDER BY created_at;
```

После исправления причины `failed` оператор может вернуть конкретную запись в
`pending`, сохранив её `id` (eventKey), `recipient_ref`, `subscription_id`, `binding_id`, `issuer` и `subject`.
Не создавать новую запись и не переоткрывать `delivered`/`cancelled`; у отозванного
получателя новое согласие не должно восстанавливать старые события.

В тестах используется только локальный HTTP test transport Portal. Реальные
Telegram-запросы и сообщения клиентам не выполняются.

## Настройка и запуск

Версионируемый порядок включения, ответственные, точные команды и откат:
[deploy/telegram-production.json](../deploy/telegram-production.json). Установка
ключа и развёртывание кода сохраняют оба флага выключенными. Включение интерфейса,
контрольная доставка и постоянная работа — отдельные согласованные этапы.

Portal передаёт **один** scoped key в `/opt/familyQuest/private/telegram-service-key`
(владелец `lobov`, режим `0600`). Команда `python3 scripts/telegram-control.py install-key`
проверяет ключ read-only запросом к `https://lovit.tech/v1/telegram/readiness`,
требует точный `scope=portal_telegram`, `productId=familyquest` и атомарно обновляет
защищённый `.env`, оставляя `false/false`. Она не выпускает ключей, не заменяет
другой существующий ключ и не выводит секретов. После неё нужно пересоздать Access
командой из manifest. Перед изменением сохранить `.env` в защищённой резервной копии.

`enable-ui` требует свежего входящего транспорта Portal; `enable-delivery` — его
полной готовности `ready/linked`. Эти команды применяются **после** согласования
соответствующего этапа. `disable` не обращается к Portal: откат доступен при сетевой
ошибке. Уже поставленную очередь Portal останавливает его оператор отдельно;
receiver следует сохранить для обработки `/stop`.

Приватная диагностика: `docker exec familyquest-access-1 familyquest-telegram-status`.
Выход `0` означает готовность транспорта; `2` — выключенную или неготовую зависимость.
Команда не создаёт Telegram-сессию, не ставит уведомлений и не публикует данные в HTTP.
Она отклоняет чужой продукт, неизвестное состояние, повреждённый ответ, redirect,
неработающий или устаревший worker. Access атомарно обновляет heartbeat в `/tmp`
после работы с каталогом/семьёй и при остановке. Это только состояние процесса;
согласия и очередь по-прежнему принадлежат PostgreSQL. Ошибка каталога/Core не
исчезает из диагностики до успешного полного обхода. Порог свежести — 45 секунд,
запрос каталога ограничен 10 секундами, семейный batch — 30 секундами.

При включённом outbox Docker healthcheck дополнительно выполняет эту проверку;
при выключенном остаётся обычная проверка веб-сервиса. Health не доказывает пустую
локальную очередь ошибок: `notification-status` проверяется отдельно для каждой семьи.
Portal `failed` может включать исторические ошибки; при наличии `recentFailed`
используется его актуальный счётчик согласно контракту Portal.

SDK-разрешение на сообщения учитывается строго: только `true` допускает opt-in.
Отказ, неподдерживаемый метод, исключение или отсутствие callback в течение 30 секунд
оставляют уведомления невключёнными. Повторного скрытого согласия нет.

Каталог `backend/seed` и частные env-файлы исключены из Docker build context;
они не попадают даже в промежуточный слой сборки. SaaS отклоняет непустой seed path,
а `DATABASE_URL` обязателен и не имеет встроенных учётных данных. Новая семья
содержит только введённый родительский профиль, без готовых задач и наград.

Требуется SaaS-топология [Access](access-service.md) с OIDC и настроенной точной
связью аккаунта с семьёй. Домашний режим без Access работает как прежде, но
Telegram-вход в нём не включается.

```dotenv
TELEGRAM_ENABLED=false
TELEGRAM_OUTBOX_ENABLED=false
TELEGRAM_PORTAL_ORIGIN=https://lovit.tech
TELEGRAM_SERVICE_KEY=<existing-familyquest-product-service-key>
```

В Compose Access передаёт эти параметры. Получатели и события хранятся в Core
PostgreSQL; `TELEGRAM_RECIPIENTS_FILE` больше не используется. Worker запускается
только при отдельном `TELEGRAM_OUTBOX_ENABLED=true` и включённом Telegram.
Оба флага остаются `false`; при паузе worker события сохраняются в PostgreSQL.
Продуктовый ключ хранится только в secret store,
не в Git. Это отдельный от ACCESS_SHARED_SECRET, OIDC client secret и входного
LOVIT_READ_TOKEN ключ. На Portal нужны настроенный бот `familyquest`, продуктовый
ключ, `TELEGRAM_ENABLED=true`; доставка первоначально
`TELEGRAM_DELIVERY_ENABLED=false`.

Перед обновлением Core применить семейные миграции штатным
`familyquest-operator migrate`. Миграция `011_notification_outbox.sql` создаёт
очередь без backfill старых действий; `012_notification_bindings.sql` добавляет
Portal binding. Старые записи consent без binding отключаются, legacy pending
отменяются с кодом `binding_upgrade`; история delivered сохраняется. Для них
нужно новое явное согласие, нельзя угадывать binding или переносить его из UI.
На production перед этим обновлением обе таблицы пусты, Telegram выключен.

Штатный migrator повторно выдаёт семейным ролям права; SQL-права Access не
расширяются. Порядок: backup → приостановить provisioner → применить миграции
новым operator → обновить Core/Access/provisioner/web → проверить health, версии,
схемы и оба выключенных флага. Не менять уже применённые миграции.

```bash
# Подставить локальные/операторские параметры через защищённое окружение.
docker compose -f docker-compose.prod.yml -f docker-compose.access.yml config --quiet
docker compose -f docker-compose.prod.yml -f docker-compose.access.yml build api access web
# Развёртывание и включение флага выполняет оператор отдельно после проверки.
```

Для просмотра без Telegram: `npm --prefix frontend run dev`, путь `/telegram`
покажет безопасный переход к обычному входу. Для самостоятельного frontend
используйте прежний `VITE_API_URL`/reverse proxy, предпочтительно один origin.

В BotFather для отдельного бота «Семейные дела» настройте Main Mini App и menu button:
`https://familyquest.example.com/telegram`. Бот-токен и webhook secret хранятся
**в Portal**. Webhook идёт в Portal `/telegram/webhooks/familyquest`; настройки
и `secret_token` соответствуют общему контракту. Пример без настоящих секретов:

```text
https://t.me/example_family_bot?startapp=review
https://t.me/example_family_bot?startapp=assign
```

Разрешённые подсказки: `tasks`, `review`, `assign`, `rewards`, `settings`.
`rewards` открывает планер с начислениями за дела; arbitrary URL/ID семьи в параметре
игнорируется. После входа роли по-прежнему определяют доступные разделы.
Тема, viewportStableHeight, system/content safe area и BackButton обрабатываются
SDK-адаптером; обработчики удаляются при размонтировании. Nginx разрешает Telegram
iframe только на `/telegram`, обычные страницы сохраняют X-Frame-Options: DENY.
