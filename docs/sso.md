# Единый вход для продуктов

Принято 27.09.2026; описание реализации сверено с кодом 28.10.2026: общий аккаунт и SSO для подключённых продуктов. Подписки остаются продуктовыми. FamilyQuest сохраняет собственные профили, PIN, устройства и предметные роли.

## Реализованный адаптер

Access умеет подключаться к внешнему OpenID Connect provider. `internal/identity` не зависит от семейных моделей или billing. Provider является отдельным сервером идентификации и владельцем взрослого пароля. Разработку собственного OAuth/OIDC-сервера эта интеграция не требует.

- Authorization Code с PKCE S256, случайными state/nonce и одноразовым серверным состоянием на 10 минут.
- Проверка подписи RS256/ES256, issuer, audience, срока, nonce и authorized party. Токены соседнего продукта отклоняются.
- Host-only HttpOnly Secure cookie связывает ответ с тем браузером, который начал вход. SameSite=Lax нужен для возврата от provider.
- Callback перенаправляет на фиксированную страницу приложения без токенов/subject в URL. Затем одноразовый HttpOnly cookie (60 секунд) и same-origin POST завершают вход. Состояние ограничено по размеру и хранится в памяти процесса; перезапуск требует повторить незавершённый вход. Несколько реплик потребуют общего хранилища state/handoff или привязки запросов к экземпляру.
- Привязка `issuer + subject → семья` создаётся только оператором. Email не связывает аккаунты автоматически. Access разрешает только список профилей и вход по PIN; JWT владельца, используемый внутренним запросом к Core, клиенту не передаётся. Семейный JWT выдаётся после выбора профиля и проверки его PIN; токены OIDC не подменяют семейные роли.
- При включённом SSO публичный вход по локальному паролю отключён. Пустой/частичный набор настроек не должен приводить к незаметному fallback: если задано хотя бы одно OIDC-поле, проверяются все поля.

Для production разрешены HTTPS URL; HTTP разрешён только для loopback в тестах. У клиента только scope `openid`: email и профиль для сопоставления не требуются. Провайдер должен возвращать стабильный subject; pairwise subject разных клиентов может различаться — связь с общим billing customer создаётся отдельно доверенным оператором, не угадывается по строке sub.

## Конфигурация и включение

1. Развернуть общий стандартный OIDC provider с собственной БД, публичным DNS и HTTPS. Создать отдельный confidential client `familyquest`; разрешить только точный callback `https://<адрес приложения>/api/account/callback`. Не использовать wildcard redirect URI, implicit или password grant.
2. Перенести существующего владельца в IdP с сохранением проверенного bcrypt-хеша, если выбранный provider это поддерживает; открытый пароль не читать и не записывать в конфигурацию. Сверить перенос на отдельной тестовой записи. Если импорт несовместим — согласовать смену пароля отдельно, а не выполнять её скрыто.
3. Сохранить полный backup приложения и IdP. Обновить каталог через `familyquest-operator migrate`, затем `grant-access` для runtime-роли Access. Новая `fq_platform.identities` содержит только связь с внешней identity, не пароль.
4. Оператор `bind-identity` читает из stdin:

```json
{"Issuer":"https://auth.example.com/issuer","Subject":"immutable-provider-subject","FamilyID":1,"Operator":"operator-id"}
```

Повтор той же привязки безопасен. Переназначение существующего issuer/subject на другую семью отклоняется. В этой версии адаптера одна identity привязана к одной семье FamilyQuest; выбор из нескольких семей ещё не реализован. Другие продукты имеют собственные привязки и не используют эту таблицу.

5. Добавить в защищённую `.env` все четыре поля `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_REDIRECT_URL`. Compose overlay передаёт их только Access. В frontend нет client secret.
6. Перезапустить Access и web согласованной сборкой. `/api/config` возвращает `sso:true`, форма заменяется кнопкой «Войти с единым аккаунтом». Пройти полный вход владельцем и проверить свои данные. До принятия этих проверок прежний production-вход не отключать.

`GET /api/account/authorize` начинает вход, `GET /api/account/callback` завершает OIDC, `POST /api/account/exchange` с `X-FamilyQuest: 1` однократно создаёт сессию аккаунта и возвращает список профилей. `POST /api/account/restore` восстанавливает список по cookie аккаунта, `POST /api/account/profile` проверяет выбранный профиль и PIN и возвращает его семейный JWT. Сессия аккаунта живёт 12 часов; выбор «запомнить» увеличивает срок до 30 или 60 дней. При заданном `SSO_SESSION_FILE` реестр сессий и отзывов сохраняется в приватном файле; Compose подключает отдельный том. Незавершённый OIDC state/handoff по-прежнему хранится только в памяти. При недоступности provider или неверных токенах доступ не предоставляется. При ошибке нужно вернуться в приложение и начать вход заново.

## Выход и отзыв

«Выйти» отзывает текущую локальную SSO-сессию, очищает cookie аккаунта и устройства, запрашивает отзыв устройства в Core и возвращает `logoutUrl`. Frontend переходит на `end_session_endpoint` из OIDC discovery с фиксированным адресом возврата. Без доступного endpoint операция возвращает 503. Завершение общей IdP-сессии требует успешного перехода браузера к провайдеру.

`POST /api/account/backchannel-logout` принимает подписанный logout token. Проверяются issuer, audience, срок, `iat`, `jti`, отсутствие nonce, событие logout и sid/subject. Реестр отзывает соответствующие SSO-сессии и хранит запрет повторного создания 30 дней. Access требует действующую SSO-cookie вместе с семейной сессией, поэтому уже выданный JWT обычного браузера не обходит этот отзыв. Реестр рассчитан на один экземпляр Access; несколько реплик требуют общего хранилища с согласованным отзывом.

Это не универсальная обработка всех событий блокировки IdP. Без доставки logout-события немедленный отзыв по внешней блокировке не гарантирован. MCP-делегирования имеют самостоятельный срок и отзыв; они намеренно работают без SSO-cookie и отзываются через управление MCP, смену PIN или блокировку семьи. Приватный Core не должен быть доступен в обход Access.

## Вход через LOVIT и запоминание

`LOGIN_PORTAL_URL=https://lovit.tech/login?product=familyquest` включает переход на
LOVIT после проверки сохранённого входа. Настройка необязательна: без неё остаётся
продуктовая кнопка входа. Сначала `SessionStartup` восстанавливает профиль; если он
действует, открывается продукт. Если сохранён только взрослый SSO-аккаунт, открываются
выбор профиля и PIN. Если аккаунта нет, происходит переход на LOVIT. Ошибка сети,
непривязанная identity и ошибка callback остаются видимыми, без цикла переходов.

На LOVIT пользователь выбирает текущий сеанс, 30 или 60 дней. Запрос
`/api/account/authorize?remember=0|30|60` связывает выбор с серверным OIDC flow,
`state`, PKCE и браузером; callback не может изменить срок. Старое `remember=1`
означает 30 дней. Другие значения и дубликаты отклоняются до начала OIDC.
Текущий сеанс ограничен 12 часами на сервере, cookie не имеет Max-Age.
Для 30/60 дней совпадают срок cookie и срок серверного реестра. Браузер может
восстанавливать session cookie вместе с вкладками; явный выход завершает вход.
Выбор срока не отменяет PIN и не меняет подписку семьи.

## Проверки и статус

Тестовый OIDC provider действительно подписывает ID tokens и проверяет PKCE. Автоматически проверены чужие issuer/audience, nonce, authorized party, просроченный токен, state, отсутствие cookie, повтор callback/handoff; два независимых clientId получают общую identity, но не принимают чужой audience. Сквозной тест с PostgreSQL проверяет явную привязку, отказ непривязанному пользователю, обмен на семейную сессию и отключение локального парольного входа.

Историческая проверка 27.09.2026, не повторённая в аудите 28.10.2026: выполнен браузерный acceptance с реальным IdP: тестовый пользователь входит на LOVIT, затем открывает FamilyQuest без повторного пароля. Непривязанная identity не получает доступа к семье. Проверка межпродуктовых платных прав потребует реализации универсального биллинга.

27.09.2026 развёрнут ZITADEL 4.16.0 на `auth.lovit.tech` с отдельной PostgreSQL 17 и login UI. Проверены HTTPS и OIDC discovery. Инфраструктура описана в [инструкции](../deploy/identity/README.md). Созданы отдельные confidential clients для FamilyQuest и LOVIT Studio. Владелец перенесён по bcrypt-хешу без сброса пароля и явно привязан к семье 1. На момент этой проверки production FamilyQuest 0.3.0 работал с `sso:true`, локальный парольный вход отключён. В браузере проверены вход тестового пользователя на LOVIT, переход в FamilyQuest без повторного пароля и отказ непривязанному аккаунту в доступе к семье. Тестовая запись деактивирована, её IdP-сессии отозваны. Вход реального владельца с его паролем должен подтвердить сам владелец. Универсальное хранилище биллинга остаётся отдельным этапом из [архитектуры](multiproduct-billing.md).
