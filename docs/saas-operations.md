# Подключение семей и эксплуатация SaaS-пилота

Операторская программа входит в backend Docker-образ как `familyquest-operator`; локально: `go -C backend run ./cmd/operator <команда>`. Запускайте из корня репозитория или backend, чтобы находились миграции. `DATABASE_URL` у оператора указывает на административную учётную запись; у API — на отдельную рабочую. Пароли передаются через stdin, не через аргументы команды, Git или журнал терминала.

Команды, кроме migrate, читают один JSON-объект из stdin. Примеры ниже — структуры для файлов с ограниченными правами, не действительные credentials. Передавайте файл через `< /secure/input.json`, после использования удаляйте из рабочего процесса хранения секретов.

## Инициализация

1. Сделать полный PostgreSQL dump и сохранить роли/grants отдельно; проверить восстановление на другой БД. Остановить внешний трафик до переключения режима.
2. Запустить `familyquest-operator migrate` с административным DATABASE_URL: создать каталог и обновить существующие семейные схемы.
3. Подключить семью через provision либо claim-legacy. Claim требует имя и действующий PIN существующего parent и не заменяет его данные. Роль владельца привязывается к аккаунту, его профиль нельзя удалить/исключить импортом.
4. Создать отдельного SQL-пользователя API с LOGIN, NOINHERIT, без superuser, CREATEROLE, CREATEDB, BYPASSRLS; назначить индивидуальный пароль безопасным административным способом. Выполнить `grant-runtime` для этого пользователя. После добавления новых семей повторять эту команду.
5. Запустить API с `FAMILYQUEST_SAAS=1`, `FAMILYQUEST_SKIP_MIGRATIONS=1`, runtime DATABASE_URL, случайным SESSION_SECRET и HTTPS-прокси. Проверить `/api/config` → `{"saas":true}`, а без входа `/api/participants` → 401.
6. Проверить вход владельца, изоляцию двух тестовых семей, backup/restore, дату рождения и учёт оплаты. Открывать доступ только после этих проверок.

Обычные Compose-файлы передают обе переменные, по умолчанию они 0. Домашняя установка автоматически не становится SaaS. `FAMILYQUEST_SEED_FILE` в SaaS не используется. Без `SKIP_MIGRATIONS=1` API может выполнять DDL для локального тестирования; этот режим не заменяет отдельного оператора в production.

## Форматы команд

`provision` создаёт новую изолированную семью и возвращает familyId. Email уникален, один владелец на семью. `claim-legacy` использует такую же структуру, но присоединяет существующую public-схему; повторное присоединение одной схемы не допускается.

```json
{"Name":"Название семьи","Email":"owner@example.com","Password":"<индивидуальный пароль 12–72 байта>","Parent":"Имя взрослого","PIN":"<его 6 цифр>","Operator":"идентификатор оператора"}
```

`grant-runtime`:

```json
{"Role":"familyquest_runtime"}
```

`registry` — страница до 100 записей, следующая offset=100 и т.д. Содержит email владельца, поэтому результат хранить как служебные данные:

```json
{"Offset":0}
```

`payment` — ручное подтверждение уже полученных денег. Сумма — целое число минимальных единиц валюты; пример 10000 BYN означает 100,00 BYN и не является ценой продукта. Даты задаются явно, endsAt строго позже startsAt; startsAt не может быть в будущем. Reference — уникальный идентификатор внешнего документа. Не использовать новую reference для повторной доставки одной оплаты.

```json
{"familyId":1,"reference":"bank-document-unique-id","amountMinor":10000,"currency":"BYN","startsAt":"2026-09-26T00:00:00Z","endsAt":"2026-10-26T00:00:00Z","childLimit":3,"operator":"operator-id"}
```

`refund` фиксирует полный возврат в журнале, не переводит деньги через банк. Выполнять после фактического возврата/подтверждённой отмены платежа. Частичный возврат не поддерживается. Повтор команды безопасен:

```json
{"Reference":"bank-document-unique-id","Operator":"operator-id"}
```

`suspend` / `resume` блокируют/разблокируют семейный доступ. Resume не продлевает оплату:

```json
{"FamilyID":1,"Operator":"operator-id"}
```

`reset-account` — восстановление оператором после проверки личности владельца вне приложения. Меняет пароль аккаунта и отзывает сессии владельца; не меняет детские PIN:

```json
{"Email":"owner@example.com","Password":"<новый индивидуальный пароль>","Operator":"operator-id"}
```

## Восстановление и обновление

JSON v6 своей семьи восстанавливается родителем с PIN-confirmation. Подписку и аккаунт этим файлом изменить нельзя. Импорт чужой семьи, legacy v1–v5 в SaaS, credentials в файле, исключение владельца и превышение детского лимита отклоняются. Для прежней домашней копии сначала восстановить её в отдельную домашнюю установку безопасным существующим способом, затем claim-legacy; не менять familyId вручную ради переноса между клиентами.

Перед обновлением остановить API-запись, сделать системный backup, запустить operator migrate и grant-runtime, затем новый API. Убедиться, что runtime-роль по-прежнему не имеет административных атрибутов. У API нет автоматического отката миграций. Откат старого бинарника или FAMILYQUEST_SAAS=0 после подключения клиентов не является безопасным rollback.

Режим SQL-ролей проверен на обычном PostgreSQL 17. Для Yandex Managed PostgreSQL назначение и сохранение пользовательских ролей нужно проверить отдельным acceptance-тестом через интерфейсы облака; текущая CLI не объявляется готовой интеграцией с управлением ролями этого сервиса.
